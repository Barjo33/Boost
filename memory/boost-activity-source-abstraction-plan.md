**Goal (Tim, 2026-06-28):** All step-count and HR-based Boost work must support whatever the user actually uses — Garmin / AAPS Wear / alternative watch / phone — via ONE abstraction. Same design in Android (Boost-V6) AND Trio.

**Why this came up:** activity-load shadow baseline DIED at the 06-26→27 midnight rollover (`activityLoad: no baseline chosen=none cov=[]`). Root cause: daily completed-day totals read from **Health Connect ONLY** (`HealthConnectStepsIngest.chooseSourceByCoverage`), and Garmin stopped syncing steps to HC. Meanwhile HR never broke because HR is ALREADY unified (Garmin+Wear+HC all write one `heartRate` table; consumers read source-agnostic). See [[boost-v6-experimental-state-2026-06-27]], [[boost_step_source_garmin_2026-06-17]], [[boost_activity_load_sensitivity_design]].

**Diagnosis — the asymmetry:** HR = one canonical store, many writers, source-agnostic consumers (GOOD). Steps = THREE disjoint pipelines: daily (HC-only), intraday (Wear `stepsCount` table OR phone `StepService` by freshness), and `stepsCount` table (Wear-only writer). Daily had no fallback → single point of failure.

**Locked design decisions:**
- **No user-facing source selector.** Each signal auto-resolves its source internally (per-signal: steps resolver + HR resolver), invisible to the user — honours the minimal-settings tenet. (Effectively "separate per-signal, both Auto, hidden.")
- **Daily baseline = canonical store + HC backfill (HYBRID).** Derive daily completed-day totals from the same canonical step store as intraday (kills the HC single-point-of-failure); use HC only to backfill history for the chosen source on cold start. Keep baseline+intraday SAME-SOURCE for consistency.
- **Sequence: Android first → shadow-validate on nstest3 (~days) → then mirror in Trio.**

**Auto-resolution policy (steps) — TWO separate concerns (Tim 2026-06-28):**
- **Selection** (who owns TODAY's count): rank Wear(worn) > Garmin > other HC > phone; active = highest-trust source with a FRESH feed (else highest-trust with any recent data). Does NOT gate on history. → `StepSourceResolver.kt` (built).
- **Coverage / bridging** (the rolling baseline window): when the primary device CHANGES and the new device has zero/insufficient days, fill the rolling-7-day window with HISTORIC data from the OLD source so coverage is never lost — NO warmup reset on device switch. Keep per-source histories so the old source's days are available to bridge. OPEN nuance: sources count different absolute step totals, so bridged old-source days should ideally be SCALED to the new source's level via overlapping-day calibration (raw splice if no overlap) — decision pending. Bridging lives in `DailyStepHistoryTracker` (to build).
- Emit resolved source + per-source coverage/freshness to NS so a silent source death is visible.

**HR:** already unified — minimal change. Add an HR source resolver that records the resolved feeding source to NS and (optionally) keeps learned baselines keyed to a consistent source; keep current write-all / read-all consumers.
