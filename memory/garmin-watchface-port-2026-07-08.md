**ARCHITECTURE (verified vs current CIQ docs):**
- Garmin WATCH FACE cannot receive phone push (Mobile-SDK messaging is data-field/widget/app only). Wear's "AAPS Wear app pushes complications" model does NOT port.
- Only pattern: watch-face **background ServiceDelegate** → `Communications.makeWebRequest` on temporal event (HARD 5-min floor) → `Application.Storage` → face `onUpdate` reads. Request is **BT-bridged through the paired phone** (no phone/BT online → -104, no data); standalone only on LTE/WiFi Garmins.
- **SOURCE = AAPS phone HTTP server, NOT Nightscout (Tim, 2026-07-08: "it needs to talk to AAPS... our plumbing doesn't allow Nightscout").** AAPS Garmin plugin already runs an HTTP server on the phone (`127.0.0.1:28891`, pref `communication_http_port`, OFF BY DEFAULT → enable). Watch `makeWebRequest` is BT-bridged THROUGH the phone by Garmin Connect Mobile, so `127.0.0.1` = the phone → watch pulls AAPS-local directly (how the existing AAPS Garmin DATA-FIELD works). **BUT the current HTTP payload carries ZERO Boost fields** → REQUIRED AAPS-side change (Tim's fork): extend `GarminPlugin.kt` HTTP responder to emit slim Boost-enriched JSON `{bg,delta,direction,iob,cob,variable_sens(=DynISF),boostV5_state,tir,status,ts}`. DynISF = `variable_sens` (mg/dL/U). **Phase-0 must-verify:** a watch-FACE background ServiceDelegate can reach 127.0.0.1:port through the bridge (data-field does; ~90% carries to face type; fallback = CIQ native-push → tiny widget → face reads Storage).

**KEY RISKS:** (S1 → RESOLVED by AAPS-local decision) memory: no longer parsing a fat NS `devicestatus` blob — the AAPS server returns slim CONTROLLED JSON, so it IS the "server-side trim proxy" and TIR/DynISF work on MIP too. Keep the payload scalars-only. (M3) AMOLED always-on capped ~10% pixels → full-colour ring/hero can't stay lit wrist-down (dimmed ambient layer, materially different look). Fonts not pixel-reproducible (bake .fnt). (M4) swissalpine template license unverified → study/reimplement, don't fork.

**TWO WORKSTREAMS (Tim, 2026-07-08): A = display faces (out to screen, cosmetic); B = HR/steps INTO AAPS from Garmin (the real prize — fixes the documented overnight-HR-loss). DO B FIRST.** Overnight-HR-loss cause = F4: Oppo Wear OS `HeartRateListener.kt:74` callback dies overnight, no watchdog → HR dark ~2/hr; band-aid = wear watchdog + force-stop. Garmin has NO listener-death mode (24/7 HR is OS-native sleep-tracking) + can BACKFILL on BT reconnect (streaming can't).
**Workstream-B acceptance criterion: HR must be FINER than 15-min AVERAGING, peaks preserved.** Current AAPS Garmin path delivers only a 15-min HR *average* = wrong statistic (smears the short spikes exercise detection keys on; Boost added hrBpmMax5m/Min5m for exactly this — HR review F5). 15-min is an IMPL limit not a Garmin limit (Garmin records HR at seconds; data-field=1Hz, `ActivityMonitor.getHeartRateHistory` = sub-min history). Target payload `{samples[]~1min, max5m, min5m, latest}` NEVER a bare average. Even the always-on FACE background (5-min-floored) can read getHeartRateHistory(last 5min) + send 1-min samples + 5-min max/min per cycle → 1-min res w/ peaks in 5-min batches (enough for exercise/sleep detection); true 1Hz needs a data-field/app (not always-on). Face-vs-datafield achievable resolution is the Phase-0 unknown. AAPS-side: GarminPlugin.kt:388 has an HR path — verify it INGESTS Garmin HR, where the 15-min limit lives, and route fine-grained HR to the hrBpmMax5m sink. **RESOLVED (both agents done, 2026-07-08 — refs garmin_hr_resolution.md + aaps_garmin_hr_ingest.md):**
- **A+B = ONE bidirectional watch-face project + one 5-min background ServiceDelegate.** OUT: GET AAPS 127.0.0.1 → BG/IOB/DynISF/TIR → draw. IN: `getHeartRateHistory(5min)` → 1-min samples + true 5-min MAX/MIN → POST AAPS. No separate app needed — the FACE background CAN source fine HR (confirmed).
- `getHeartRateHistory` = ~1 sample/MIN modern devices, reads Garmin's already-logged 24/7 HR (~zero extra battery), AOD does NOT coarsen stored history, history persists to last power cycle. 1Hz would need foreground app (crashes in data-field) but NOT needed for 5-min peaks.
- **Overnight HR loss STRUCTURALLY SOLVED**: Garmin logs HR 24/7 in FIRMWARE regardless of app/AOD (no listener-death mode, unlike Oppo Wear); missed background slots → walk back to last-acked ts + BATCH-BACKFILL gap on reconnect (only a watch REBOOT wipes it). HC also backfills Garmin's backdated 1-min batch (2026-06-14 fix).
- **Peak-preservation FREE downstream**: Boost `hrBpmMax5m/Min5m` already `maxOf/minOf` over raw 1-min HR rows (OpenAPSBoostPlugin.kt:1601-1604). Deliver 1-min rows → peaks work, ZERO consumer change. The 15-min avg is the WEAR path (`wear/.../HeartRateListener.kt maxAverage=15`, optional), NOT Garmin.
- **AAPS change small/localized**: add `/hr` batch endpoint (mirror `/carbs`, GarminPlugin.kt:173-176) taking `{device,samples:[{t,bpm}]}` → `storeHeartRates(list)` fan-out (LoopHubImpl.kt:157-170) → shared HR table; FIX timestamp convention (Garmin uses timestamp=samplingStart; HR.kt+HealthConnect use timestamp=sample-time/duration=60000). No maxDB column needed.
- **Phase-0 verifies**: (1) face-background can reach 127.0.0.1 through the phone bridge; (2) exact CIQ background MEMORY ceiling (~28-32KB cited, unconfirmed) — background does HR-history+JSON+makeWebRequest in it; if too tight, alternate IN/OUT across cycles before splitting the app.

**STEPS added to Workstream B (Tim, 2026-07-08 — both agents done):** Garmin `ActivityMonitor.getInfo().steps` = CUMULATIVE daily counter (resets ~0 at device-midnight, may be null, NO intraday history array). 5-min background samples it + DELTAS the cumulative (cache lastStored), piggybacks the SAME 5-min HR makeWebRequest (~free, firmware-logged 24/7, AOD-independent). Midnight reset: detect by cumulative-DECREASED (cur<last ⇒ new day, delta=cur). Overnight self-healing (steps additive, overnight≈0, missed cycle merges into next delta). **Delta logic ALREADY in-tree: `StepService.stepDelta(cur,lastRaw)` = the reset-resilient accumulator (cur≥last→cur-last else cur); reuse it.** AAPS ingest = GREENFIELD (Garmin plugin has NO step handling) BUT step subsystem already source-pluralised (`StepSourceResolver.GARMIN` tier-1 exists, `IntradayStepBank` source-agnostic, `WearStepSource` adapter pattern) → build `SC(device=Garmin)`→insertOrUpdateStepsCount + adapter + bankCounts[GARMIN]; baseline/bank/sleep FREE. **★ THE REAL BLOCKER = F3 (pre-existing, bites CURRENT setup too):** live exercise classifier (`isActive`/`stepsLast15Min`, OpenAPSBoostPlugin.kt:620-623/638) reads phone `StepService` ONLY (:575-578); the SC table (wear AND future Garmin) is read for bank/baseline/sleep but NEVER the live intraday windows → even WEAR steps don't reach the classifier today. F3 fix (route resolved-source intraday windows into the classifier) is REQUIRED for Garmin-or-wear steps to change exercise state/dosing.
